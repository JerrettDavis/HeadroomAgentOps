# Dashboard maintenance

## Intent and requested outcome

Add two dashboard tools: bulk rebasing of PRs behind main, including continuity of previously approved workflow runs, and monitoring and repair of broken main CI. Review, plan, implement, land on main, relaunch, test and validate before handing the running dashboard to the user for final checks. Existing review queues, authentication, harness choices, author exclusions, publication and CI gates, and both watches must survive deployment.

## PR updates

Show every open PR targeting main whose head does not contain the current main commit. Include drafts, forks and excluded authors in this inventory; visibility grants no additional execution permission. Display number, title, author, branch, commits behind, conflict/permission status, and latest update outcome. Unknown comparison state is visibly unknown, never represented as current. Include refresh, per-row selection, select all, clear selection, update selected, and an option to reapprove previously approved workflows. Disable duplicate submissions while retaining individual outcomes and allowing other rows to finish after one fails.

Perform real Git rebases in isolated temporary checkouts. Record observed main and PR head before work, revalidate before publication, and push only with an explicit force-with-lease bound to that head. Never overwrite a concurrent author push. A successful update must contain the observed main commit. Record subsequent main movement as new drift. Do not silently substitute a merge commit. Unsupported permissions, conflicting changes, unavailable forks and changed heads go to a durable secondary queue with clear reasons and explicit retry controls.

An optional Send to agent action operates on selected secondary queue entries using the configured harness and isolated workspaces. It must actually launch remediation, persist execution and outcome, validate the result and use the same head lease before publishing. Mechanical failures must not silently become agent jobs. Agent edits that change the PR contribution require ordinary review; verified mechanical rebases reuse existing evidence silently. Do not post informational reviews, requests, comments or trigger extra AgentOps reviews merely because the base or rebased commit IDs changed. Existing watches must recognize operation receipts and verify equivalent contribution before suppression; unexpected author changes retain normal review behavior.

Reapproval is limited to a previously approved workflow identity for this PR, matching the newly observed head and reviewed execution source. Changed workflow contents, unobserved approval history or ambiguous provenance require explicit user action. Use observed run IDs, never guessed IDs. Approval continuity must work when the new workflow appears after the rebase request completes. Respect existing CI execution policy; do not grant blanket approval to new workflows.

## Main CI

Persist a main CI watch independent of the dashboard browser. Show latest main SHA, per-workflow status and links, last successful poll, incident state and error/freshness state. Alert in the application when a latest relevant workflow attempt on the current main head fails. Pending, skipped, cancelled or an API error must not be mislabeled as a new broken-main failure. Define failure conclusions as failure, timed_out, startup_failure and action_required; display action_required as approval needed and do not send it to a code fixer. Ignore superseded attempts and non-main runs. Do not mark an incident resolved merely because a new main SHA is pending; wait for observed successful relevant checks.

Default to alerts with a user-triggered Fix main action. Persist an opt-in Autofix setting that starts the same repair automatically and suppresses interrupting alerts, while retaining visible status and history. Initial defaults and UI wording are implementation choices, not prior user approvals of settings. Persist incident identity, operation claims and PR receipts so polling, retries, concurrent clicks and restart do not create duplicate repair jobs or PRs for the same failure. Group failed workflows for one head into one incident. New evidence on the same head updates the existing incident.

The configured coding harness receives bounded, redacted failure evidence and relevant logs, works on a new branch off observed main, identifies the cause, makes a targeted fix, runs relevant validation, pushes its branch and opens a repair PR. Keep this pipeline distinct from review publication. Treat logs as untrusted input. Record diagnosis, validation, execution status and the resulting PR link. No automatic merging of repair PRs: direct the user to review or fix through the dashboard. Revalidate main before publication and expose stale/inconclusive/failed attempts with explicit retry. Preserve work after interruption without claiming success or blindly launching duplicates.

## Architecture and constraints

Use the existing Python service, SQLite persistence, GitHub client, worker/harness infrastructure and plain JavaScript dashboard. Separate maintenance storage, Git operations, service orchestration and UI modules. Apply existing local API mutation authentication and redaction; never expose credentials or raw production command lines. Background work must be bounded, cancellable where safe, durable and observable. GET requests have no side effects that publish code or create repair jobs.

The service owns independent persisted settings and operation records scoped by repository. Use process ownership and transactional claims compatible with the existing recovery model. Polling errors preserve previous evidence with an explicit stale/error indicator. GitHub mutations and uncertain network outcomes are reconciled against remote state before retry. Builder decides exact schema and APIs after inspecting existing interfaces.

## Acceptance and deployment evidence

Tests must cover full drift inventory and pagination, unknown state, selection, mixed batch outcomes, forks and permissions, real Git rebase/conflict/lease rejection, restart recovery, delayed workflow appearance and approval provenance, mechanical-review suppression versus substantive author edits, main incident classification and deduplication, autofix persistence and actual harness-to-PR lifecycle with controlled fixtures. Browser checks must exercise both views, alert/autofix behavior and remediation selection. Run affected regression and repository CI before landing; verify main commit and CI remotely.

Use a state-preserving guarded reload, never stop a live panel with queued work. Reconcile the current deployed Visual Benchmark Studio source with the landing branch so deployment does not remove existing functionality. Capture queue/config/watch/auth invariants before and after without exposing secrets. Validate live routes, rendered controls and monitoring after deployment. Separate fixture evidence from live write actions: do not bulk rebase unrelated production PRs, reapprove arbitrary workflows or manufacture a broken production main merely to demonstrate controls. Report any unavailable live validation candidly, with fixture proof and remaining user checks.
